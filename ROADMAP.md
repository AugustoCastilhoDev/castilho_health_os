# Castilho Health OS — Roadmap

Repo: https://github.com/AugustoCastilhoDev/castilho_health_os
Última atualização: 2026-08-04 (Documentos com papel timbrado — cabeçalho/rodapé/assinatura/carimbo em PDF, tela de Configurações da clínica — implementado e verificado ao vivo)

## Stack

Backend: Go (Fiber) + GORM/Postgres + Redis (provisionado, ainda não usado) + Docker Compose.
Frontend: React + TypeScript + Vite + Tailwind CSS v4 + react-router-dom (`frontend/`).
Nginx + Certbot prontos para a VPS, ainda não deployados (deploy fica por último, por decisão do usuário).

## O que já existe

### Domínio e persistência
- **Modelos** (`internal/domain/models`): `Tenant`, `User`, `Patient`, `Appointment` (+ `AppointmentStatusLog`), `FinancialRule`, `FinancialTransaction`, `MedicalRecord`, `DocumentTemplate`, `PatientDocument`, `MemedPrescriptionLog`, `StockItem` + `StockMovement`, `OdontogramaEntry`. `User` ganhou `CPF`/`BirthDate`/`Sex`/`Phone` (todos opcionais — só usados pelo cadastro de prescritor na Memed). `UserRole` ganhou `PSYCHOLOGIST`/`PSYCHIATRIST` (2026-08-04); `MedicalRecord`/`Appointment` ganharam `CID` (texto livre, opcional). `Tenant` ganhou `AddressStreet`/`AddressCity`/`AddressState`/`AddressZip`/`LogoKey` (papel timbrado); `DocumentTemplate` ganhou `IncludeHeader`/`IncludeFooter`/`IncludeSignature`/`IncludeStamp` (flags de layout do PDF).
- **Migrations** (`migrations/`, formato golang-migrate): 13 pares up/down cobrindo o schema atual, com `CHECK` constraints espelhando os enums do Go.
- **Repositórios** (`internal/repository`): um por agregado, todos com `tenant_id` explícito em toda query (nunca confia só no campo da struct). `AppointmentRepository.TransitionStatus` roda em transação com `SELECT FOR UPDATE`, valida a máquina de estados e grava o audit log atomicamente.

### Auth e API
- **JWT + bcrypt + RBAC** (`internal/auth`, `internal/api/middleware`): claims carregam `tenant_id`/`role`; `RequireAuth` + `RequireRole` protegem as rotas.
- **Services** (`internal/service`): Auth (login com erro genérico contra enumeração), Tenant (onboarding atômico clínica+admin + `Get`/`UpdateProfile` para perfil da clínica + `CreateLogoUploadURL`/`SetLogo`/`DeleteLogo`/`LogoDownloadURL`/`GetLogoBytes` para o logotipo, ver seção própria), User (CRUD + troca/reset de senha), Patient, Appointment, Financial, Settlement, MedicalRecord (CRUD com trava de `IsLocked`), DocumentTemplate (CRUD + `Generate`, agora monta `pdf.RenderOptions` a partir das flags do template + `DocumentBranding` fornecido pelo handler), PatientDocument (presigned upload/download via R2, ver abaixo), Memed (cadastro/token de prescritor + log de auditoria de receita, ver seção própria).
- **HTTP API** (`internal/api`, Fiber): `/auth/register`, `/auth/login`, `/api/tenant` (GET + `PUT` admin-only) + `/api/tenant/logo*` (upload em duas etapas + download-url + delete, admin-only), `/api/me`, `/api/users/*`, `/api/patients/*`, `/api/appointments/*` (+ transições de status, + `/settle` manual), `/api/financial-rules/*`, `/api/financial-transactions/*`, `/api/medical-records/*` (+ `/:id/lock`), `/api/document-templates/*` (+ `/:id/generate`, retorna PDF binário com papel timbrado), `/api/patients/:patientID/documents/*` (upload em duas etapas) + `/api/patient-documents/:id/*` (download/exclusão), `/api/memed/token` (token do prescritor), `/api/patients/:patientID/memed-prescriptions` (log de auditoria) + `/api/memed-prescriptions/:id/cancel`, `/api/stock-items/*` (+ `/:itemID/movements` para registrar/listar entradas e saídas, + `/import` upload multipart de CSV), `/api/patients/:patientID/odontograma` (gráfico atual) + `/api/patients/:patientID/odontograma-entries` (histórico completo) + `/api/odontograma-entries` (registrar achado, dentista-only).
- **CORS** (`internal/config` + `cmd/api/main.go`): `CORS_ALLOWED_ORIGINS` (default `http://localhost:5173`) — necessário pro frontend chamar a API cross-origin em dev. Também expõe `Content-Disposition` (`ExposeHeaders`) para o frontend conseguir ler o nome do arquivo gerado.
- **Cloudflare R2** (`internal/config` + `cmd/api/main.go`): `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET_NAME` — opcionais (`Config.IsR2Configured()`); se ausentes, o app sobe normalmente e só o upload/download de documento fica indisponível (`503`, `service.ErrStorageNotConfigured`). Configurados de verdade em 2026-07-28 (conta e bucket reais do usuário).
- **Memed** (`internal/config` + `cmd/api/main.go` + `internal/memed`): `MEMED_API_KEY`/`MEMED_SECRET_KEY` — opcionais (`Config.IsMemedConfigured()`), mesmo padrão do R2; sem eles o app sobe normalmente e só a emissão de receita fica indisponível (`503`, `service.ErrMemedNotConfigured`). `MEMED_API_URL`/`MEMED_FRONTEND_SCRIPT_URL` já vêm com default apontando pro sandbox público da Memed.
- **Settlement financeiro automático** (`internal/service/settlement_service.go`): gera o `PROFESSIONAL_PAYOUT` sozinho assim que as duas condições de gate são satisfeitas — `Appointment.Status == COMPLETED` e existe um `FinancialTransaction` do tipo `PATIENT_PAYMENT` com `Status == PAID` para aquele agendamento. Disparado best-effort a partir de dois pontos: `AppointmentHandler.Transition` (quando a transição resulta em `COMPLETED`) e `FinancialHandler.MarkPaid`. Idempotente via `FindPayoutBySource`; se nenhuma regra financeira aplicável existir ainda, fica pendente e pode ser reprocessado manualmente via `POST /api/appointments/:id/settle` (role `finance`).

### Frontend (`frontend/`)
- **Design system**: paleta "Clean Tech" (slate/sky/emerald/rose) aliada como tokens semânticos (`bg-brand-*`/`text-brand-*`) em `src/index.css` (`@theme` do Tailwind v4).
- **Auth real** (`src/lib/auth/AuthContext.tsx`): login contra `/auth/login`, JWT decodificado no cliente só para exibição (nunca confiado — a API sempre revalida), sessão persistida em `localStorage`, `ProtectedRoute` guardando o app.
- **Telas**: Login, Dashboard (contadores do dia), Agenda Semanal (grade CSS Grid, cores por status, criação de agendamento e transições de status via modal — transicionar pra `COMPLETED` abre um passo intermediário pra informar um CID opcional, mesmo padrão visual já usado pro motivo de cancelamento), Pacientes (busca + cadastro/edição completos + **Prontuário/PEP**, ver abaixo), **Financeiro** (Lançamentos + Regras de Repasse), **Documentos** (modelos de documentos, ver abaixo), **Usuários** (administração de usuários, ver abaixo). Todas com dados reais da API, não mockados.
- **Lacunas conhecidas da integração**: não existe endpoint "todos os agendamentos de hoje da clínica" (só por profissional) — resolvido no frontend com um seletor de profissional (`useProfessionalScope`) quando o usuário logado não é um profissional de saúde (`HEALTH_PROFESSIONAL_ROLES` em `lib/roles.ts`: `DOCTOR`/`DENTIST`/`PSYCHOLOGIST`/`PSYCHIATRIST`). Não existe endpoint de faturamento agregado — o Dashboard soma as transações de cada agendamento individualmente (aceitável na escala atual).
- **CID (diagnóstico)** — pedido em 2026-08-04, junto com os papéis de Psicólogo/Psiquiatra: campo de texto livre (sem validação contra a tabela oficial CID-10, ~14 mil códigos — v1 é "deixar o profissional digitar", não um catálogo pesquisável) em três lugares — `MedicalRecord.CID` (campo "CID" no formulário de evolução, aparece na timeline do prontuário quando preenchido), `Appointment.CID` (informado ao concluir o atendimento, guardado direto no agendamento — não só via o `MedicalRecord` ligado por `AppointmentID` — pensando numa futura integração de faturamento por convênio/TISS que provavelmente consulta agendamentos, não prontuários) e `{{cid}}` em modelos de documento (já funcionava sem nenhuma mudança de código — mecanismo genérico de tags). Backend: coluna `cid VARCHAR(255)` nullable em `medical_records`/`appointments` (migration 000012); `AppointmentRepository.TransitionStatus` ganhou um parâmetro `cid` que só sobrescreve o valor quando não-vazio (uma transição sem CID informado preserva o que já estava gravado, em vez de apagar).
- **Financeiro** (`src/pages/FinancialPage.tsx`): duas abas.
  - **Lançamentos**: lista paginada de `FinancialTransaction` (recebimentos e repasses) com filtro por situação/tipo, botão "Registrar Pagamento" (cria `PATIENT_PAYMENT` via busca de paciente + valor + forma de pagamento + convênio opcional) e "Marcar como pago" por linha (só aparece para quem já é `TENANT_ADMIN`/`FINANCE` — o backend também restringe via `finance` middleware). Dois cards de resumo (A Receber / A Repassar pendentes) somam até 100 linhas pendentes de cada tipo — mesmo tipo de limitação aceita do Dashboard, não há endpoint de soma agregada.
  - **Regras de Repasse**: seletor de profissional (reaproveita `useProfessionalScope`) + tabela de `FinancialRule` com CRUD completo pela tela — "Nova Regra" e "Editar" (`RuleFormModal.tsx`: tipo percentual/fixo, escopo procedimento/convênio, dedução de taxa, prioridade) e "Ativar/Desativar" por linha (visível só para `TENANT_ADMIN`/`FINANCE`, backend restringe via `finance` middleware).
  - Backend ganhou `GET /api/financial-transactions` (novo — antes só existia por agendamento): `FinancialTransactionRepository.ListByTenant` com filtro por `Type`/`Status` + paginação (`FinancialService.ListTransactions` default 20/máx 100 por página), coberto por teste de repositório.
  - Backend ganhou `PUT /api/financial-rules/:id` (novo — o service já tinha `UpdateRule`, mas sem handler/rota): validação (`validateRule`, compartilhada com `CreateRule`) e semântica PUT de substituição completa — `is_active` omitido é zerado, então o frontend sempre envia a regra inteira.
- **Prontuário / PEP** (`PatientRecordPage.tsx` + `components/prontuario/`): a linha do tempo do paciente mistura `Appointment` e `MedicalRecord` (evoluções clínicas) num único histórico ordenado por data, cada tipo com seu próprio visual. "Novo Registro"/"Editar" (`MedicalRecordFormModal.tsx`, usa o editor rich-text — ver `RichTextEditor` abaixo) e "Finalizar registro" (trava `IsLocked`, depois disso o registro fica só-leitura) aparecem para qualquer papel de profissional de saúde (`DOCTOR`/`DENTIST`/`PSYCHOLOGIST`/`PSYCHIATRIST` — backend restringe via middleware `health`). O campo "Tipo" da evolução pré-seleciona (mas não trava) o tipo correspondente ao papel de quem está logado (`DEFAULT_RECORD_TYPE_BY_ROLE` em `lib/medicalRecord.ts`) — ex: um `PSYCHOLOGIST` abre o formulário já em "Evolução Psicológica". Um campo "CID" (texto livre, opcional — ver seção própria abaixo) fica logo abaixo do Tipo. "Gerar Documento" (`GenerateDocumentModal.tsx`) lista os modelos ativos, extrai via regex as tags `{{...}}` do modelo escolhido além das 3 automáticas (`patient_name`/`professional_name`/`date`, sempre resolvidas no backend, nunca confiadas do cliente) e baixa o PDF gerado.
  - **Editor rich-text** (`components/common/RichTextEditor.tsx`, Tiptap/ProseMirror): toolbar com negrito/itálico/lista com marcadores/lista numerada/desfazer/refazer; `MedicalRecord.Content` agora guarda o HTML serializado do editor (`editor.getHTML()`) em vez de texto simples. `PatientTimeline.tsx` renderiza esse HTML sanitizado com DOMPurify (`dangerouslySetInnerHTML`) — sanitização é defesa em profundidade, já que só `DOCTOR`/`DENTIST` do próprio tenant conseguem escrever o conteúdo. CSS dedicado (`.rich-content` em `index.css`) restaura o estilo padrão de `<p>`/`<ul>`/`<ol>`/`<strong>`/`<em>` que o preflight do Tailwind remove, sem puxar o plugin `@tailwindcss/typography` inteiro. Verificado ao vivo via Playwright — achou e corrigiu um bug real: os botões da toolbar roubavam o foco do editor no `mousedown` antes do `chain().focus()` do Tiptap rodar, corrompendo a seleção/cursor (texto/itens de lista embaralhados); corrigido com `onMouseDown={(e) => e.preventDefault()}` em cada botão.
  - **Documentos anexados** (`PatientDocumentsPanel.tsx` + `UploadDocumentModal.tsx`): upload real em duas etapas — (1) `POST .../documents/upload-url` devolve uma URL presignada, (2) o navegador dá `PUT` direto no R2 (os bytes nunca passam pelo nosso servidor), (3) `POST .../documents` grava só o metadado. "Baixar" busca uma URL presignada de leitura e abre em nova aba (arquivos sem `Content-Disposition: attachment` — como `.txt`/imagem — abrem inline, é comportamento normal do navegador, não bug). "Excluir" é `TENANT_ADMIN`-only, remove o metadado e, best-effort, o objeto no R2.
  - **Receitas (Memed)** (`MemedPrescriptionsPanel.tsx` + `IssuePrescriptionModal.tsx`): lista o log de auditoria (data + status) e, para papéis com registro que permite prescrever (`DOCTOR`/`DENTIST`/`PSYCHIATRIST` — `PRESCRIBER_ROLES` em `lib/roles.ts`, espelha `UserRole.CanPrescribe()` no backend), um botão "Emitir Receita" que busca o token do prescritor (`/api/memed/token`), carrega o script da Memed (`lib/memed.ts`) e abre o widget deles — o conteúdo da receita nunca passa por este app. `PSYCHOLOGIST` é profissional de saúde (escreve evoluções) mas não vê esse botão — psicólogo não tem registro que permita prescrever no Brasil (CRP, não CRM/CRO). Ao capturar o evento `prescricaoImpressa` do widget, grava o log via `POST .../memed-prescriptions`.
- **Documentos** (`DocumentTemplatesPage.tsx` + `DocumentTemplateFormModal.tsx`): CRUD de `DocumentTemplate` (criar/editar/ativar-desativar), restrito a `TENANT_ADMIN` na tela e no backend (`admin` middleware) — listar fica aberto a qualquer papel autenticado, pois é o que alimenta o "Gerar Documento" do Prontuário. A tag `{{cid}}` já funciona num modelo sem nenhuma mudança de código — o mecanismo genérico de extração de tags (`GenerateDocumentModal.tsx`) trata qualquer `{{tag}}` fora das 3 automáticas como um campo de preenchimento manual. O formulário ganhou 4 checkboxes de layout do PDF (ver seção "Papel timbrado" abaixo).
- **Papel timbrado (PDF)** — pedido em 2026-08-04: os documentos gerados (atestados/laudos/declarações) deixaram de ser só título + texto puro e agora suportam 4 blocos opcionais, configuráveis por modelo (`DocumentTemplate.IncludeHeader`/`IncludeFooter`/`IncludeSignature`/`IncludeStamp`, todos `true` por padrão num modelo novo criado pela tela):
  - **Cabeçalho**: logotipo da clínica (centralizado, altura fixa 14mm, largura calculada pela proporção real da imagem) + nome + CNPJ/CPF + endereço, com uma linha fina separando do corpo. Desenhado via `doc.SetHeaderFunc` do `go-pdf/fpdf` — repete em toda página, não só na primeira.
  - **Rodapé**: telefone e e-mail centralizados, via `doc.SetFooterFunc` — usa a convenção do fpdf de `SetY` negativo ("medido a partir do fim da página"), então funciona independente de quantas páginas o documento tiver.
  - **Assinatura**: "[Cidade], [Data por extenso em português]" seguido de uma linha pontilhada centralizada (`SetDashPattern`) — desenhado uma única vez, no fim do corpo do texto, nunca repetido por página.
  - **Carimbo**: nome do profissional + registro no formato "CRM/SP 123456" (monta a partir de `CouncilType`/`CouncilState`/`CouncilNumber`, já existentes em `User`) — só aparece se `IncludeStamp` estiver ligado *e* `IncludeSignature` também (o carimbo fica abaixo da linha de assinatura, não é um bloco independente).
  - Nenhuma biblioteca nova — tudo construído em cima do `go-pdf/fpdf` que o projeto já usava (`internal/pdf/generate.go`), deliberadamente sem trocar para Maroto/gofpdf puro como chegou a ser cogitado, já que a lib atual já resolve acentuação em português (`UnicodeTranslatorFromDescriptor`) e trocar de biblioteca era um risco desnecessário pro que foi pedido.
  - **Configurações** (`ConfiguracoesPage.tsx`, nova tela, link na sidebar só pra `TENANT_ADMIN`): formulário de perfil da clínica (nome/CNPJ-CPF/e-mail/telefone/endereço, `PUT /api/tenant`) + upload de logotipo (mesmo padrão de duas etapas do upload de documento de paciente, reaproveitando o R2). Sem essa tela não haveria como preencher os dados que o cabeçalho do PDF usa — não existia nenhuma edição de perfil da clínica antes disso.
  - `AuthContext` ganhou `refreshTenant()` — depois de salvar o perfil, recarrega o tenant no contexto pra sidebar mostrar o nome atualizado sem precisar de logout/reload.
- **Usuários** (`UsersPage.tsx` + `components/usuarios/`): CRUD de `User` — lista (nome/e-mail/papel/situação), "Novo Usuário"/"Editar" (`UserFormModal.tsx`: nome/e-mail/papel/senha e, quando o papel é um profissional de saúde, os campos de registro profissional — conselho/número/UF/CPF/nascimento/sexo/telefone; disponíveis mesmo pra `PSYCHOLOGIST`, que não prescreve, pois CRP é registro profissional válido por si só). O select "Papel" inclui `PSYCHOLOGIST`("Psicólogo(a)")/`PSYCHIATRIST`("Psiquiatra") desde 2026-08-04; escolher um papel pré-seleciona (mas não trava) o tipo de conselho esperado (`DEFAULT_COUNCIL_TYPE_BY_ROLE`: CRM pra `DOCTOR`/`PSYCHIATRIST`, CRO pra `DENTIST`, CRP pra `PSYCHOLOGIST`). "Redefinir senha" (`ResetPasswordModal.tsx`, admin define uma nova senha sem precisar da atual) e "Ativar/Desativar" (bloqueado para o próprio usuário logado, evitando autodesativação acidental). Tela e ações restritas a `TENANT_ADMIN` (link na sidebar só aparece pra admin); backend já reforçava isso via middleware `admin` em `Create`/`Update`/`ResetPassword` — só faltava a UI.
- **Estoque** (`EstoquePage.tsx` + `components/estoque/`): lista de `StockItem` (nome/unidade/quantidade/situação, badge "Estoque baixo" quando `quantity_on_hand <= min_quantity`), "Novo Item" (`StockItemFormModal.tsx`: nome/unidade/estoque mínimo opcional + quantidade inicial opcional, que vira uma entrada real no histórico em vez de um número solto), "Editar" (não altera quantidade — só nome/unidade/mínimo/ativo), "Movimentar" (`StockMovementModal.tsx`: registra uma entrada ou saída) e "Histórico" (`StockMovementHistoryModal.tsx`: lista as movimentações do item com data/tipo/quantidade/quem registrou/nota — resolve o nome de quem registrou via `GET /api/users/:id`, mesmo padrão já usado no Financeiro para nome de paciente/profissional). Gerenciar itens é restrito a `TENANT_ADMIN`/`RECEPTIONIST` (mesmo grupo que registra pagamento de paciente); listar/ver histórico fica aberto a qualquer papel autenticado. "Importar CSV" (`StockImportModal.tsx`, mesmo grupo `frontDesk`) sobe um arquivo via `multipart/form-data` (`POST /api/stock-items/import`) e mostra um resumo com contadores de criados/pulados/com erro + tabela detalhando linha/nome/motivo de cada pulo ou falha; um link "Baixar modelo CSV" gera um exemplo client-side (`Blob` + link temporário, sem chamada à API). Colunas reconhecidas (case-insensitive, ordem livre): `nome`/`name` e `unidade`/`unit` (obrigatórias), `quantidade_minima`/`min_quantity` e `quantidade_inicial`/`initial_quantity` (opcionais) — parser em `internal/api/handlers/stock_handler.go` (`encoding/csv`, sem dependência nova).
- **Odontograma** (`OdontogramaPanel.tsx` + `components/prontuario/`, dentro do Prontuário do paciente): dois gráficos lado a lado — dentição permanente (32 dentes, notação FDI 11-48) e decídua (20 dentes, 51-85) — sempre exibidos juntos (não alterna por idade do paciente, já que dentição mista é clínica e normal). Cada dente é um botão colorido conforme a condição mais recente (legenda com as 9 condições: Saudável/Cárie/Restaurado/Ausente/Canal/Coroa/Implante/Fraturado/Indicação de extração); clicar num dente abre `OdontogramaEntryModal.tsx` para registrar um novo achado (condição + nota opcional). "Histórico" (`OdontogramaHistoryModal.tsx`) lista todos os achados já registrados do paciente (data/dente/condição/quem registrou/nota), mesmo padrão do histórico de Estoque. Registrar um achado é `DENTIST`-only (papel novo em `router.go`, mais restrito que o grupo `health` usado no resto do prontuário, já que este módulo é odonto-exclusivo); visualizar o gráfico/histórico fica aberto a qualquer papel autenticado, como o resto do prontuário. Verificado ao vivo via Playwright: 52 blocos de dente renderizam corretamente, registrar um achado atualiza a cor/rótulo do dente na hora, um segundo registro no mesmo dente substitui o estado exibido sem duplicar o bloco (confirma a query `DISTINCT ON`), o histórico mantém as duas entradas completas, a UI bloqueia o clique para papéis não-dentistas, e a API rejeita tanto um `tooth_number` inválido (400) quanto uma tentativa de `RECEPTIONIST` registrar um achado (403).

- **CI** (`.github/workflows/ci.yml`): GitHub Actions rodando gofmt/vet/build/test (com Postgres de serviço + migrations aplicadas) e um build do Dockerfile, a cada push/PR na `main`. **Verde.**
- **Testes**: 109 automatizados (backend) — 73 de serviço (mocks, sem banco, inclui um teste que gera um PDF completo com cabeçalho/rodapé/assinatura/carimbo e logotipo real sem erro, e um teste que confirma um logotipo malformado degrada pra "sem logo" em vez de derrubar a geração inteira — ver dívida técnica) + 31 de repositório (integração, banco real, inclui um teste de concorrência real com 10 goroutines disparando movimentações de estoque simultâneas contra o mesmo item, confirmando que o `SELECT ... FOR UPDATE` serializa e o saldo final bate; um teste que confirma a query `DISTINCT ON` do Odontograma retorna só a entrada mais recente por dente, não o histórico inteiro; um teste que confirma o `cid` de um `Appointment` persiste e é preservado em transições subsequentes sem `cid`; um teste de `StockItemRepository.FindByName` case-insensitive; e um teste que documenta a regra correta do GORM pra flags booleanas com `default` — ver decisões de arquitetura) + 2 de `internal/domain/models` (`UserRole.IsHealthProfessional`/`CanPrescribe` para os 7 papéis, incluindo os dois novos) + 3 de `internal/memed` (cliente HTTP contra um `httptest.Server` fake, incluindo o regression guard do bug do envelope `data` encontrado ao vivo). Fluxos de frontend (login, agenda, CRUD de paciente, settlement, financeiro, PEP, upload de documento contra o R2 real, emissão de receita via Memed, administração de usuários, editor rich-text, estoque, odontograma, papéis de psicólogo/psiquiatra + CID, importação de estoque via CSV, papel timbrado + Configurações da clínica) validados manualmente ponta a ponta com Playwright headless a cada rodada — a verificação do PDF de papel timbrado usa `pdf-parse` (dependência temporária, instalada/desinstalada na mesma rodada) pra extrair o texto real do PDF gerado e confirmar que cada bloco (nome/CNPJ/endereço da clínica, nome/registro do profissional, data por extenso) aparece de fato no conteúdo — não só que o PDF não está vazio. Não há suíte automatizada de frontend ainda. Sem testes de handler HTTP (dívida técnica já aceita) — a lógica de parsing do CSV (`parseStockImportCSV`) só é coberta pela verificação ao vivo, mesmo padrão do resto do pacote `handlers`.

## PEP / Documentos / Receitas

Pedido em 2026-07-27: gestão de Documentos, Receitas e Evolução Clínica. Três decisões tecnológicas oficiais do projeto:

1. **Arquivos externos (exames, laudos de terceiros)**: Cloudflare R2 (S3-compatible), acesso via **presigned URLs** geradas no Go (`internal/storage/r2.go`, usando `aws-sdk-go-v2`) — o servidor nunca vê os bytes do arquivo, só autoriza upload/download por um tempo curto. `PatientDocument` guarda só metadados (`FileKey`, nome, tamanho, mimetype).

## Decisões de arquitetura para lembrar

- **Multi-tenant**: `tenant_id` sempre vem do JWT (claims), nunca do payload do cliente.
- **Dinheiro**: sempre `int64` em centavos, nunca `float64`.
- **PUT = substituição completa**: campos omitidos são zerados — exceto em `User`, onde `PasswordHash` é protegido explicitamente (load-then-mutate no service) porque não faz parte do DTO de update.
- **RBAC em duas camadas**: a maioria das rotas usa `RequireRole` na própria rota; a restrição de quem pode criar um `PROFESSIONAL_PAYOUT` mora no service, porque depende do campo `type` do corpo da requisição, que o middleware de rota não enxerga.
- **Agendamento**: transição de status só acontece via `TransitionStatus`, que é a única operação que grava em `appointments` e `appointment_status_logs` — nunca two-step.
- **Arquivos nunca passam pelo nosso servidor**: R2 é acessado só via presigned URL, gerada sob demanda, com expiração curta — vale tanto para upload quanto para download.
- **Backend nunca é dono do conteúdo da receita médica**: a Memed é o sistema de registro da prescrição; o Go só audita (quem, quando, qual ID).
- **Estoque é ledger + saldo derivado**: `StockItem.QuantityOnHand` nunca é editado diretamente (nem pelo `PUT /api/stock-items/:id`, que só toca nome/unidade/mínimo/ativo) — a única forma de mudar o saldo é `StockMovementRepository.RecordMovement`, que faz `SELECT ... FOR UPDATE` no item, aplica o delta e grava o log numa única transação (mesmo padrão do `AppointmentRepository.TransitionStatus`). Até "quantidade inicial" ao criar um item vira uma movimentação `IN` de verdade (nota "Estoque inicial"), não um número solto sem explicação no histórico.
- **Odontograma é ledger sem tabela de estado atual**: diferente do Estoque, `OdontogramaEntry` não tem uma tabela-irmã tipo `StockItem` guardando o estado corrente — uma mudança de condição de dente é uma substituição pura (não um delta numérico), então não há saldo para proteger com transação/lock. O "gráfico atual" é computado direto na leitura via `DISTINCT ON (tooth_number) ... ORDER BY tooth_number, created_at DESC` (`OdontogramaRepository.CurrentChart`), coberto por teste de repositório que garante duas entradas no mesmo dente colapsam pra uma no gráfico mas continuam as duas no histórico completo (`ListByPatient`).
- **`IsHealthProfessional()` vs `CanPrescribe()`**: dois predicados deliberadamente diferentes em `UserRole` (`internal/domain/models/user.go`). `IsHealthProfessional` (`DOCTOR`/`DENTIST`/`PSYCHOLOGIST`/`PSYCHIATRIST`) controla quem pode ser `ProfessionalID` num `Appointment`/`FinancialRule` e quem escreve um `MedicalRecord` (grupo `health` no router). `CanPrescribe` (`DOCTOR`/`DENTIST`/`PSYCHIATRIST`, sem `PSYCHOLOGIST`) controla só o acesso à Memed (grupo `prescribers`, mais estreito) — psicólogo é profissional de saúde de pleno direito mas não tem registro que permita prescrever no Brasil (CRP, não CRM/CRO). Espelhado no frontend como `HEALTH_PROFESSIONAL_ROLES`/`PRESCRIBER_ROLES` em `lib/roles.ts`.
- **`validRole()` em `user_service.go` é uma segunda lista independente de papéis válidos** — separada de `UserRole.IsHealthProfessional()`/`CanPrescribe()`. Achado ao vivo nesta sessão: adicionar `PSYCHOLOGIST`/`PSYCHIATRIST` ao enum sem atualizar esse switch deixava `POST /api/users` rejeitando os dois papéis novos com "unknown role", mesmo já sendo membros válidos do enum Go. Agora tem teste de regressão (`TestUserService_Create_AcceptsNewHealthProfessionalRoles`) — lembrar de checar esse switch sempre que um papel novo for adicionado.
- **CID vive tanto no `MedicalRecord` quanto no `Appointment`, sem um ser derivado do outro**: parecido com a decisão de não fazer o Odontograma derivar de uma tabela de estado, mas na direção oposta — aqui a duplicação é deliberada. `MedicalRecord.AppointmentID` já linka os dois, então dava pra só ler o CID via join; guardar também no `Appointment` direto foi escolha explícita do usuário, pensando numa futura integração de faturamento por convênio que provavelmente consulta agendamentos, não prontuários.
- **Importação de Estoque via CSV reaproveita `CreateItem` linha a linha, em vez de um caminho de bulk-insert separado**: cada linha válida vira uma chamada normal a `StockService.CreateItem` (mesma validação, mesmo "quantidade inicial vira uma movimentação IN de verdade" do fluxo manual) — trocando uma import mais rápida por garantir que não existem dois caminhos de criação de item com regras diferentes. Duplicata é detectada por `StockItemRepository.FindByName` (case-insensitive) *antes* de chamar `CreateItem`, nunca por deixar o banco rejeitar — não há `UNIQUE` constraint em `stock_items.name` (duas linhas de nomes iguais em tenants diferentes são normais).
- **Slice combinado em Go precisa de `make(..., 0, ...)` explícito, não só `append`**: achado ao vivo — `append(parseIssues, result.Failed...)` no handler de import, quando ambos os lados estavam vazios, devolvia `nil` (não um slice vazio), que o `encoding/json` serializa como `null`. Isso quebrava o frontend (`result.failed.length` em cima de `null`) toda vez que uma importação não tinha nenhuma falha. Corrigido construindo o slice combinado via `make([]T, 0, cap)` + dois `append`s. Vale lembrar desse padrão em qualquer lugar futuro que combine slices que podem vir vazias/nulas antes de devolver como JSON.
- **GORM só pode ter UM dos dois: campo bool com `default:` na tag, OU capacidade de persistir `false` explícito no `Create`** — não os dois ao mesmo tempo. Achado ao vivo (bug real, não só de teste): `DocumentTemplate.IncludeHeader` (e as outras 3 flags de layout) tinham `gorm:"...;default:true"`; GORM omite do `INSERT` qualquer campo cujo valor Go seja o zero-value do tipo *e* cuja tag tenha `default` — pra um `bool`, isso torna `false` (a escolha real do usuário ao desmarcar um checkbox) indistinguível de "não veio preenchido", e o banco aplicava `DEFAULT TRUE` por baixo dos panos. Um modelo criado com todos os checkboxes desmarcados saía do banco com tudo `true`, gerando o papel timbrado completo mesmo assim. Corrigido removendo `default:true` da tag Go (a coluna do banco continua com `DEFAULT TRUE`, só não é mais o mecanismo real de correção — isso agora é 100% responsabilidade do valor Go explícito). `Update` nunca teve esse problema, porque já usa `Select("*")` (sempre manda toda coluna, independente de zero-value) — o bug era exclusivo do `Create`. Vale lembrar desse padrão em qualquer `bool`/`default` futuro onde `false` precisa ser um valor real e intencional, não só "ainda não preenchido".
- **`go-pdf/fpdf` pode falhar de duas formas bem diferentes num decoder de imagem malformada**: `panic` de verdade (slice fora do range, achado ao vivo com um PNG mal-formado escrito à mão num teste) *ou* setar sua própria flag de erro interna (`f.Err()`) sem panicar — nesse segundo caso, todo método do `fpdf` vira no-op silencioso a partir dali, inclusive `Output()`, então o PDF inteiro falha por causa só do logo. `drawLogoSafely` (`internal/pdf/generate.go`) trata os dois: `recover()` pro panic, e `doc.ClearError()` sempre que `doc.Err()` for true depois de registrar/desenhar a imagem — assim um logotipo ruim vira "cabeçalho sem logo", nunca "documento não gerado".

## Dívida técnica consciente (decisões, não esquecimentos)

- Sem hard-delete de usuário — só desativação (`is_active=false`), pra não quebrar histórico de agendamento/repasse.
- Sem proteção contra o último `TENANT_ADMIN` se autodesativar/rebaixar (ficaria um tenant sem admin).
- Quem pode disparar qual transição específica de agendamento (ex: só o profissional atribuído inicia `IN_PROGRESS`) não é restrito por role — só a máquina de estados protege contra pulos ilegais.
- Sem testes de handler HTTP nem suíte automatizada de frontend (ambas as camadas validadas manualmente/via Playwright a cada rodada).
- Redis provisionado no compose mas nada usa ainda (sem sessão/cache).
- Quem pode disparar o `/settle` manual é `finance`/`admin`, mas não há alerta/fila visível para "agendamentos completos sem repasse pendente".
- Settlement paga sempre 100% do valor calculado de uma vez (`PENDING`); não há parcelamento nem estorno automático se o `PATIENT_PAYMENT` for cancelado depois que o payout já foi gerado.
- Dashboard/Agenda fazem N+1 de lookups (nome de paciente/profissional, transações por agendamento) — aceitável na escala atual, primeiro candidato a otimizar se a base crescer.
- Quem pode editar/travar um `MedicalRecord` não é restrito a "só quem escreveu" — qualquer `DOCTOR`/`DENTIST` do tenant pode editar/finalizar o registro de outro profissional, mesmo padrão de "sem restrição por ownership" já aceito nas transições de agendamento.
- Registros clínicos criados antes do editor rich-text têm `Content` em texto simples (sem tags) — o CSS de renderização (`.rich-content` + `whitespace-pre-wrap`) trata isso de forma segura, mas não há migração retroativa desses registros pro formato HTML do novo editor (não havia necessidade — eram só dados de teste em dev).
- Deletar um `PatientDocument` remove o objeto do R2 só best-effort (log, não erro) — se a chamada de delete no R2 falhar, o metadado já foi removido e o objeto fica órfão no bucket (invisível pro app, mas ainda ocupando espaço).
- CORS do bucket R2 é configurado manualmente no painel da Cloudflare (não pelo app) — ao apontar pra um domínio de produção, alguém precisa lembrar de adicionar esse domínio em `AllowedOrigins` lá, senão o upload quebra silenciosamente só em prod.
- Pré-preenchimento do paciente (`setPaciente`) no widget da Memed não foi confirmado ao vivo — o campo "Nome" continuou com o placeholder mesmo após corrigir os nomes de campo e o timing; o profissional precisa digitar manualmente por enquanto (não bloqueia o uso, só perde a conveniência do auto-preenchimento).
- `MemedService.RecordIssuance` marca `IssuedAt` com o horário do servidor no momento em que recebe a chamada do frontend, não o horário real em que a Memed processou a emissão — pode haver uma pequena defasagem se a chamada de log falhar/atrasar.
- Sem tela de auto-cadastro de senha/"esqueci minha senha" — o admin redefine a senha de qualquer usuário via `/api/users/:id/reset-password` (tela de Usuários), mas não há fluxo de reset por e-mail.
- Estoque v1 é só entrada/saída manual (`StockMovementType` = `IN`/`OUT`, sem um terceiro tipo "ajuste" com sinal) — decisão deliberada do usuário para manter o modelo de dados simples; uma correção de contagem vira uma saída (ou entrada) com nota explicando o motivo, em vez de um conceito de delta com sinal. Quantidade é sempre inteira (sem frações tipo ml/mg) — também decisão do usuário, cobre a maioria dos itens de uma clínica (caixas, unidades, frascos fechados).
- Erros do backend (`repository.ErrInsufficientStock`, `ErrInvalidTransition`, `ErrLocked`, etc.) chegam ao frontend como a string técnica do Go (ex: "repository: insufficient stock quantity"), não uma mensagem traduzida — confirmado ao vivo no modal de movimentação de estoque. É o mesmo comportamento já aceito em outras telas (nenhuma camada de tradução de erros de API existe hoje); não foi corrigido agora para não abrir escopo de uma refatoração maior de mensagens de erro fora do que foi pedido.
- Sem vínculo entre consumo de estoque e procedimentos/agendamentos — decisão deliberada do usuário para a v1: descontar itens automaticamente ao realizar um procedimento fica para uma eventual v2, quando/se fizer sentido modelar quais itens cada procedimento consome.
- Odontograma v1 registra só o dente inteiro (`ToothCondition`), sem granularidade por face (mesial/distal/oclusal/vestibular/lingual) — decisão deliberada do usuário: um gráfico mais simples de construir e ler, mesmo padrão de "escopo v1 reduzido, só entrada/saída" adotado no Estoque. Uma face problemática vira uma nota de texto na condição do dente inteiro, não um sub-registro por face.
- Registrar um achado do Odontograma é restrito a `DENTIST`, não ao grupo `health` (`DOCTOR`+`DENTIST`) usado no resto do prontuário — decisão de design (não pedida explicitamente pelo usuário) alinhada à descrição do roadmap do módulo como "exclusivo odonto"; um `DOCTOR` não consegue registrar achados de dente mesmo estando autorizado a escrever no prontuário geral do mesmo paciente.
- Sem edição/exclusão de um achado do Odontograma já registrado (mesmo padrão do `StockMovement`: histórico é append-only) — uma correção vira um novo achado com nota explicando o motivo, não uma edição do registro anterior.
- CID é texto livre sem validação contra a tabela oficial CID-10 (~14 mil códigos) — decisão deliberada do usuário para a v1: um catálogo pesquisável fica pra uma eventual v2, se/quando fizer sentido investir numa fonte de dados oficial. Hoje nada impede um profissional de digitar um código inexistente ou mal formatado.
- `Appointment.CID` pode ser definido em qualquer transição de status, não só ao completar (`TransitionStatus` aceita `cid` como parâmetro opcional independente de `to`) — a UI só oferece o campo no passo de conclusão (`COMPLETED`), mas a API não impede registrar um CID cedo (ex: ao confirmar). Não é validado contra o status da transição de propósito, pra não travar um fluxo real onde o diagnóstico já é conhecido antes do atendimento.
- `MedicalRecord.CID`/`Appointment.CID` usam `gorm:"column:cid"` explícito — sem isso, o naming strategy padrão do GORM quebra `CID` em `c_id` (trata só o sufixo `ID` como initialism, não a palavra inteira `CID`), o que não bate com o nome real da coluna criada pela migration. Achado ao vivo (erro `column "c_id" of relation "medical_records" does not exist` rodando os testes de repositório) — lembrar desse padrão em qualquer campo futuro cujo nome termine com uma sigla de 3+ letras que inclua "ID" (`CID`, não `UUID`/`URL` etc., que o GORM já reconhece como initialism inteiro).
- Importação de Estoque via CSV só cria itens, nunca atualiza um existente — decisão deliberada do usuário (opção recomendada nas duas perguntas de escopo): duplicata (mesmo nome, case-insensitive) é sempre pulada e reportada, nunca sobrescreve nome/unidade/mínimo de um item já cadastrado. Uma atualização em massa via CSV fica pra uma eventual v2, se/quando fizer sentido.
- CSV de importação não tem limite de tamanho próprio — usa o `BodyLimit` padrão do Fiber (4MB), suficiente pra uma lista de itens de estoque de qualquer clínica realista, mas não há uma mensagem de erro amigável se alguém subir um arquivo gigante por engano (a requisição só falha genericamente).
- Linhas malformadas do CSV (parse quebrado, coluna a mais/a menos) são reportadas com a mensagem genérica "linha malformada", sem indicar qual caractere/coluna especificamente causou o problema — normalmente é suficiente pra alguém abrir a linha no Excel e corrigir visualmente, mas não é um diagnóstico detalhado.
- Cabeçalho/rodapé do papel timbrado são desenhados de novo em cada página (`SetHeaderFunc`/`SetFooterFunc`), mas o logotipo tem tamanho fixo (14mm de altura, largura pela proporção real) — não há como ajustar isso por modelo ou por clínica; uma logo muito larga (ex: horizontal/wordmark) pode ficar desproporcionalmente pequena. Suficiente pro pedido atual, mas não é configurável.
- Endereço da clínica é sempre montado numa única linha ("Rua - Cidade/UF - CEP XXXXX-XXX") sem opção de formato alternativo (ex: complemento, bairro) — os campos structs (`AddressStreet`/`City`/`State`/`Zip`) já existem separados no banco, então adicionar mais um campo (bairro/complemento) no futuro é aditivo, não uma migração destrutiva.
- Upload de logotipo aceita qualquer imagem que o navegador mande como `image/png`/`image/jpeg` no `<input accept>`, mas o backend não valida de verdade o conteúdo do arquivo (mime type real, dimensões, tamanho máximo) — um arquivo renomeado pra `.png` mas com outro conteúdo passaria pelo upload e só falharia (silenciosamente, virando "sem logo" — ver decisão de arquitetura sobre `drawLogoSafely`) na hora de gerar um PDF.
- `TenantService.UpdateProfile` não permite editar `Slug`/`Type` — decisão deliberada (não pedida explicitamente, mas alinhada ao resto do app): `Slug` é o identificador de login, mudar isso silenciosamente quebraria o hábito de login de todo mundo da clínica; `Type` controla quais módulos aparecem no frontend, uma mudança mais estrutural que "editar o perfil". Se precisar mudar algum dos dois no futuro, é uma operação separada, não parte da tela de Configurações.
